# Request digest specification

Normative. Two implementations that receive the same request must compute the
same digest, or "same call id, different payload" is undetectable across a
boundary — each runtime self-consistent, and disagreeing with the other about
whether a replay is a replay.

The algorithm previously lived only in a JavaScript function while the schema
accepted any non-empty string. Rust and Python could conform to every schema
and vector and still disagree.

## 1. Domain

The preimage begins with the domain string, followed by `\n`:

```
actions-json/request-digest/v1
```

Output is prefixed `req-`.

## 2. Preimage

UTF-8 text, five lines:

```
<domain>\n
<primitive>\n
<primitive_version or "-">\n
<provider or "-">\n
<canonical(arguments)>\n
```

**Contract and provider identity are part of the request**, not context around
it. Installation revision is deliberately absent from the receipt store key —
an unrelated config change must not invalidate outstanding calls — but that
leaves a gap: after live capability state changes, the same call id and payload
could replay a receipt produced under a materially different primitive contract
or a different provider. Binding these two closes it without reintroducing the
wedge, because they change only when what would actually execute changes.

A literal `-` marks an absent value, so "no provider" and a provider literally
named `-` are distinguishable from an omitted field only if that name is
disallowed; provider ids are opaque and this reference implementation does not
mint one.

No JSON serializer produces the preimage. Serializer differences across
languages — key order, number formatting, escaping, whitespace — are exactly
the drift a cross-language digest must not inherit.

## 3. Canonical encoding of arguments

| value | encoding |
|---|---|
| `null` | `null` |
| boolean | `true` / `false` |
| number | shortest round-trip decimal; integers without a decimal point |
| string | JSON string, `"` and `\` escaped, **non-ASCII kept literal** (not `\uXXXX`) |
| array | `[` elements joined by `,` `]`, order preserved |
| object | `{` `"key":value` pairs joined by `,` `}`, keys sorted **byte-wise by UTF-8**, not by locale |

Array order is significant; object key order is not. That asymmetry is
deliberate: `[1,2]` and `[2,1]` are different requests, `{a,b}` and `{b,a}` are
the same one.

## 4. Algorithm

SHA-256 over the UTF-8 bytes of the preimage. Output is the lowercase hex of
the **first 16 bytes** (32 hex characters), prefixed `req-`.

## 5. Goldens

`golden-request-digests.json` carries preimage/output pairs covering empty
arguments, key-order equivalence, nested objects and arrays, Unicode, numeric
boundaries, booleans and null, and empty containers.

**They were generated by an independent Python implementation**, not exported
from the JavaScript one. A golden produced by the code it validates proves
self-consistency and nothing about conformance — which is the property this
file exists to establish. An implementation that disagrees with a listed pair
is non-conforming regardless of whether its own tests pass.
